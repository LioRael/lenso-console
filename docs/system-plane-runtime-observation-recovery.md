# Runtime Observation Recovery

The Console Service-side consumer of the managed-Service Runtime Observability
capability belongs in the Rust Lenso Service/Worker. It is not a browser API and
must never receive an operator session token.

## Contract source

The authoritative contract is generated by the framework repository at
`contracts/openapi/autonomous-service-runtime.v1.yaml`.

The future Console Service consumer will use exactly these read-only operations
from each enrolled managed Service:

- `GET /system-plane/v1` returns the authenticated Core document used for
  capability negotiation.
- `GET /system-plane/v1/runtime-observability` returns a revisioned
  `RuntimeObservabilitySnapshot` and its opaque `nextCursor` watermark.
- `GET /system-plane/v1/runtime-observability/changes?cursor=...&limit=...`
  returns a `RuntimeObservationFeed` or an explicit Evidence Gap.

Each request uses a newly issued, audience-bound Console Service Workload
Identity credential. The request is bound to the negotiated contract, feature,
endpoint, target Service Principal, and one absolute deadline. Reads are not
automatically retried; HTTP rejection, deadline expiry, transport failure, and
wire-contract violations remain distinct.

## System Registry and Core discovery

The Console Service owns `console.managed_services` in its own Console Store.
Each row contains the stable Service Reference, the Console-side enrollment
receipt digest, grant revision, authorization epoch and expiry, plus the latest
strictly parsed Core document. It does not store or reuse a managed Service's
business users or Auth state.

Registration rejects the Console Service's own identity, expired grants,
insecure non-loopback URLs and malformed enrollment evidence. Discovery is
allowed only for an active, unexpired enrollment and must preserve the
registered Service ID, Service Principal and origin. Runtime observation is
available only when Core advertises
`lenso.system-plane.runtime-observability.v1` with both `queue-summary` and
`recovery-feed`.

Core contract or capability failures mark only that registration
`incompatible`; transport, credential, HTTP and deadline failures mark it
`unavailable`. Successful discovery marks it `ready`. Every state transition
uses the registry row version as an optimistic concurrency guard, so a stale
worker cannot overwrite a newer enrollment or discovery result.

## Projection recovery

The PostgreSQL projection stores the source Service and revision, contract and
schema digest, snapshot revision, opaque cursor, observed and Console-collected
times, freshness, collection state, and the complete replaceable snapshot.
Writes use a monotonically increasing local version as an optimistic concurrency
guard.

Reconciliation follows these rules:

1. A missing or schema-mismatched projection is replaced from a fresh snapshot.
2. An unchanged feed advances the durable cursor and collection time without
   replacing the snapshot.
3. Any Service-owned change invalidates the aggregate projection and causes one
   fresh snapshot replacement.
4. An Evidence Gap is recorded before refreshing Core discovery and fetching
   the replacement snapshot. The replacement must match the newly negotiated
   Service revision and schema digest. If rebuilding fails, the last valid
   projection and the gap evidence remain.
5. Connectivity failure marks only the affected Service projection unavailable;
   freshness is computed independently and other Services continue reconciling.
6. Console Store coordination failure is isolated from managed-Service
   availability and is never rewritten as Service failure.

Current implementation status:

- The active System Registry schema is owned by the ordinary
  `lenso/system-registry` Module at
  `service/src/modules/system_registry/migrations/0001_create_managed_service_registry.sql`.
- The schema belongs only to the independent Console Service Store and must not
  be applied to a managed Service Store.
- Runtime Observation reconciliation is a planned Console Service Worker
  capability. Its projection schema should be added as a Rust Lenso Module
  migration when that capability is implemented; it is not currently registered
  or executed by `service:migrate`.
